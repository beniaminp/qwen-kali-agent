    23 — React & Tailwind datasets: what exists, what is missing, and how to mix it¶

    Last verified: 25 October 2026. Dataset sizes and licenses were checked against the Hugging Face API and dataset cards; re-check before a large download.

    There is no single “React 19 + Tailwind 4 + good design system” dataset. What exists falls into six families:

    1. Raw code corpora — The Stack v3, filtered to JS/TS/TSX.
    2. Code instruction data — OpenCodeInstruct, Magicoder, React-specific instruction sets.
    3. Complete React apps — react-code-instructions.
    4. Design-to-code / visual data — WebSight v0.2 (HTML + Tailwind), Design2Code.
    5. Agentic front-end benchmarks — Webdev-Bench, SWE-bench Multilingual, Multi-SWE-bench, SWE-bench Multimodal.
    6. Repository sources — shadcn/ui, Tailwind, React, Radix, TanStack, Storybook, Playwright.

    The missing pieces — Tailwind 4 tokens, design-system refactors, accessibility, visual quality, testing — are exactly what synthetic generation and execution verification are for. See 25 — React synthetic data.

    2. Raw code: The Stack v3¶

    The Stack v3 is the current large open code corpus:

    • 15.9 TB training subset, ~3.6T tokens, 713 languages, 173M repositories.
    • Full corpus: 113.7 TB, 770 languages, 224M repositories.
    • ODC-BY; per-file license metadata; gated full corpus.
    • Inline file contents and language, license_type, detected_licenses.

    For React/Tailwind:

    1. Filter language to TypeScript/JavaScript/TSX/JSX.
    2. Prefer repositories with package.json, react, tailwindcss, vite.
    3. Keep permissive license_type/detected_licenses; drop unknown for a release.
    4. Sample repositories, not random files, so you get imports, components and tests together.
    5. Do not train on raw files for SFT. Use them as seed repos for synthetic tasks.

    A 50k–200k file sample is plenty for a LoRA; a 3T-token continued-pretraining run is a different project and belongs on rented GPUs.

    3. Instruction data¶

    3.1 OpenCodeInstruct¶

    • 5M instruction/answer pairs, ~19 GB, CC-BY-4.0.
    • Fields include input, output, domain, generation_algorithm, unit_tests, tests_execution_status, average_test_score.
    • Best large public starting point for code SFT, but Python-heavy and multilingual.
    • Filter to React/TS by checking for import React, tsx, useState, tailwind, className=.
    • Prefer rows with passing tests; do not assume the metadata is correct.
    • It is not a React design-system dataset; it teaches general code instruction following.

    3.2 Magicoder¶

    • OSS-Instruct-75K: MIT; generated by GPT-3.5, so OpenAI's usage policy applies.
    • Evol-Instruct-110K: Apache-2.0.
    • Good for diversity and harder reasoning; weak for React 19, Tailwind 4 and repo context.
    • Filter JS/TS; drop LeetCode-style puzzles if you want production front-end style.

    3.3 react-code-instructions¶

    • 74,428 rows, ~907 MB, MIT.
    • Complete React apps (Artifact-style) generated by Llama 3.1 70B/405B and DeepSeek Chat V3.
    • Useful for whole-app shape: routing, pages, components, mock data, styling.
    • Caveats:
    • generated by 2024-era models, likely React 18 / Tailwind 3;
    • quality varies; some apps are toy clones;
    • no tests or build verification;
    • possible brand/trademark imitation (LinkedIn clone, Apple Store clone).
    • Use it as a style/structure seed, not as gold. Rebuild, typecheck, test and retag to React 19/Tailwind 4.

    3.4 CodeSearchNet (JS)¶

    • 1,857,835 JavaScript functions; 157,988 with documentation.
    • Good for docstring→function, summarization, code search.
    • Not React, not components, not Tailwind.
    • Optional; low priority for a UI adapter.

    4. Design-to-code and visual data¶

    4.1 WebSight v0.2¶

    This is the most relevant public visual corpus for Tailwind:

    • 1,922,671 synthetic websites; screenshot + HTML + Tailwind CSS.
    • ~285 GB; CC-BY-4.0.
    • Generated from LLM website ideas, then code; real images in v0.2.
    • llm_generated_idea gives a text description you can reuse as a brief.
    • The Tailwind is from the v3 era (2024). It is not a Tailwind 4 corpus.

    How to use it:

    1. Sample 10k–50k rows; do not download 285 GB for a LoRA.
    2. Use llm_generated_idea as a design brief; use the HTML/Tailwind as a layout/class reference.
    3. Convert selected examples to React components (dangerouslySetInnerHTML → JSX) with a verified synthetic pass.
    4. Add a Tailwind 3 → 4 migration task for a subset; that teaches the renames and CSS-first config.
    5. Use screenshots for a VLM captioner, not as direct input to Qwen2.5-Coder.

    4.2 Design2Code¶

    • 484 real webpages from C4 validation; screenshot + HTML; images replaced with placeholders.
    • ODC-BY; evaluation only.
    • Metrics: rendered visual similarity (CLIP), element matching (position/text/color), block match.
    • Good for measuring visual fidelity of a design-to-code system.
    • Qwen2.5-Coder is text-only, so it cannot be evaluated on the screenshot input directly. Use a VLM front-end or convert the screenshot to a written spec first.

    4.3 The text-only rule¶

    Do not put screenshots in a Qwen2.5-Coder training row. The model cannot see them, and the template will not encode them. Options:

    • VLM caption → design spec → coder (recommended; this handbook).
    • Separate VLM adapter (Qwen3-VL class) for image → code.
    • Human-written brief for the highest-quality examples.

    A text coder trained on “design.md → code” can still produce beautiful UIs; it just needs the design expressed in words and tokens.

    5. Agentic and repository-level data¶

    5.1 Webdev-Bench¶

    • 40 composite front-end tasks over an evolving Vite + React project.
    • 188 milestones, 1,125 checklist items; functional, visual, interaction, coverage and data dimensions.
    • Seed types: PRD (20), brownfield (11), replicate (9).
    • MIT; evaluation only.
    • This is the closest public benchmark to “keep modifying a real front-end and keep it working”. It is also a good template for your own golden set: milestones + observable checklist, not a single prompt.

    5.2 SWE-bench Multilingual¶

    • 300 issue-resolution tasks; JavaScript 26, TypeScript 17.
    • Repos include preactjs/preact, vuejs/core, facebook/docusaurus, babel/babel, axios/axios, mrdoob/three.js.
    • MIT; evaluation only.
    • Good for repo-level JS/TS reasoning, but not specifically React UI or Tailwind.

    5.3 Multi-SWE-bench¶

    • 1,632 tasks; TypeScript 224, JavaScript 356.
    • other license; source repositories have their own licenses.
    • Evaluation only; do not train on the benchmark.
    • Useful for measuring multi-file edits and test-driven repair.

    5.4 SWE-bench Multimodal¶

    • 480 test + 100 dev tasks from 17 JavaScript/TypeScript repositories; issues include screenshots, mockups or diagrams.
    • No license tag on the dataset; the source repos have licenses. Treat as evaluation only.
    • This is the right benchmark if your system accepts images; not for a text-only Qwen2.5-Coder.

    5.5 What these teach¶

    • Read a file tree and find the relevant component.
    • Change multiple files without breaking imports.
    • Run the test/build command and recover.
    • Preserve behavior while refactoring.
    • Produce a patch, not a lecture.

    Single-file instruction data does not teach these. Mix repository tasks with component tasks.

    6. Repository sources: the best “design system” data¶

    There is no public “good taste” dataset. The best seed is real, permissively licensed code:

    6.1 shadcn/ui¶

    • MIT; copy-paste components built on Radix + Tailwind.
    • Excellent patterns for:
    • cn and CVA variants;
    • data-slot, data-state, aria-* styling;
    • dialogs, dropdowns, tabs, tooltips, forms;
    • dark mode tokens.
    • Do not copy the whole library into every example; extract the pattern and generate a small component.

    6.2 Radix Primitives¶

    • MIT; accessible headless components.
    • Use for focus management, keyboard interaction, ARIA, portal/overlay behaviour.
    • Training data should show composition (Dialog.Root, Dialog.Trigger, Dialog.Content) rather than reimplementing focus traps.

    6.3 Tailwind CSS repo¶

    • MIT; tests and examples for v4 features.
    • Good for edge cases: @theme, @utility, @variant, container queries, @starting-style, scrollbars.
    • Do not train on the framework's internal source as if it were app code.

    6.4 React repo¶

    • MIT; tests, fixtures, docs.
    • Good for React 19 behaviours: useActionState, useOptimistic, use, ref cleanup, View Transitions.
    • Not a UI dataset.

    6.5 TanStack Query¶

    • MIT; examples for queries, mutations, optimistic updates, invalidation, Suspense.
    • Extract patterns, not the library internals.

    6.6 Storybook and Playwright¶

    • MIT / Apache-2.0.
    • Storybook: stories, states, a11y addon, interaction tests.
    • Playwright: E2E, visual snapshots, accessibility scans.
    • These are verification sources; the training rows are the verified tasks.

    7. The gap: Tailwind 4, design systems, accessibility¶

    No public dataset reliably labels:

    • “this component uses semantic tokens instead of raw palette”;
    • “this layout has good hierarchy and spacing”;
    • “this refactor improves composition without changing behaviour”;
    • “this interaction is keyboard-accessible”;
    • “this is a Tailwind 4 migration, not a v3 example”.

    The honest approach:

    1. Mine real components from MIT repositories.
    2. Generate tasks from a working baseline: add a variant, extract a primitive, tokenize colors, add a dark theme, fix a focus trap.
    3. Verify with the compiler, tests, Playwright and axe.
    4. Grade visual quality with a rubric and a human/VLM pairwise review.
    5. Keep a human-labeled slice to calibrate the rubric.

    A component that builds, passes tests, has zero serious axe violations and looks good at 320/768/1440 is a much stronger example than a prose “make it beautiful”.

    8. The mix¶

    For a first React/Tailwind adapter, aim for 2–4M tokens (roughly 2,000–5,000 examples after truncation):

    Bucket Share Source Why
    Components/primitives 20% shadcn/ui, Radix, synthetic teaches the component shape
    Pages/layouts 15% synthetic, react-code-instructions teaches composition and hierarchy
    Data/forms 15% TanStack Query, React 19 Actions, synthetic teaches states and validation
    Design system/refactor 10% synthetic + tokens teaches consistency
    Accessibility 10% synthetic + axe teaches keyboard/focus/semantics
    Testing 10% synthetic + Playwright/RTL teaches verification
    Bug fix/recovery 10% commits, synthetic teaches multi-file reasoning
    Migration 5% synthetic React 18→19, Tailwind 3→4, Router 7→8, TS 6→7
    Negative/refusal/security 5% synthetic teaches boundaries

    A mature adapter can grow to 8–12M tokens. Scale task families, not paraphrases.

    9. Quality filters¶

    Run these before tokenization:

    • Type-check: tsc --noEmit with a TypeScript 7-compatible tsconfig.
    • Lint: ESLint 10 (TypeScript 6 API bridge), react-hooks, jsx-a11y.
    • Unit: Vitest 5 + Testing Library; tests assert behaviour via roles.
    • E2E: Playwright; critical flows pass.
    • Build: vite build; no missing imports or unresolved aliases.
    • A11y: axe serious/critical = 0.
    • Responsive: no horizontal overflow at 320, 768, 1440.
    • Tailwind 4: no @tailwind base, no bg-opacity-*, no flex-shrink-*, no dynamic class names, no outline-none on focus.
    • React 19: no ReactDOM.render, no useFormState; forwardRef/React.FC are warnings, not errors.
    • No raw hex when a token exists; inline style={{ color: ... }} is a warning.
    • No unsanitized dangerouslySetInnerHTML; no secrets; no VITE_* secrets.
    • No any/@ts-ignore/console.log/TODO in final answers.
    • License metadata present; reject unknown/non-commercial for a release.
    • Dedup exact and near-duplicate components/pages; split by repo/commit.

    scripts/validate_react_dataset.py automates the static checks. It is not a browser, compiler or test runner.

    10. Contamination and evaluation hygiene¶

    • Hold out Webdev-Bench, Design2Code, SWE-bench Multilingual (JS/TS), Multi-SWE-bench (TS/JS) and SWE-bench Multimodal.
    • Run 13-gram overlap between training rows and every benchmark.
    • Split by repository and base commit, not random row.
    • Hold out entire shadcn/ui component families, Tailwind versions or React releases for a time-based test.
    • Keep a private golden set of 100–200 tasks from your own product.
    • Report the base model and adapter on the same prompt, viewport, seed and browser.
    • For visual tasks, use pairwise human/VLM comparison, not an absolute “beauty score”.

    A model that memorizes shadcn/ui examples will look great on a shadcn clone and fail on your design system. The private golden set is the cure.
