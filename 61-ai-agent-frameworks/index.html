    61 — Agent frameworks: what to use, when and why¶

    Last verified: 28 October 2026. Every Python example was run against a local OpenAI-compatible stub; package versions are named in §15. Framework status, ownership and licences were checked against official repos, PyPI and docs in October 2026.

    52 — Agents and tool use built an agent from scratch: a model, a tool registry, a dispatcher, a loop, a stop condition — about sixty lines of plain Python. This chapter answers the question that follows: should you keep writing that yourself, or adopt a framework, and if so which one? It is a decision guide, not a catalogue. You will see what a framework actually gives you and what it costs, a procedure for deciding whether you need one, the landscape sorted into categories, one honest section per framework (the same structure every time), the same small task implemented and run against a stub in ten-plus of them so the differences are concrete, a comparison matrix and a lines-of-code count from the real files, a selection guide, the cross-cutting concerns (observability, evaluation, testing, upgrades, security, cost), and migration paths in and out.

    Read 52 first for the loop and the agentic-workflow patterns (chaining, routing, parallelization, orchestrator–workers, evaluator–optimizer), and 58 — MCP for the tool protocol every serious framework now speaks. The handbook's concrete agent — a local Qwen3-14B driving typed tools against an isolated Kali VM — is 11 — The Kali agent, whose §3.4 already compares agent harnesses (OpenCode, hackingBuddyGPT, HexStrike) for that security track; this chapter agrees with it and covers the general-purpose application frameworks instead.

    The one idea to carry through: a framework is leverage you rent, not capability you own. It removes boilerplate and adds structure, and in exchange you debug through its abstractions and follow its upgrade treadmill. Rent it when the leverage beats the baseline you just saw — and measure, do not assume.

    1. What a framework gives you — and what it costs¶

    An "agent framework" is a library that owns some of the machinery around a model so you write less of it. The good ones give you most of this list; none is magic.

    1.1 The ten things a framework can give you¶

    1. Model abstraction. One interface over many providers (OpenAI, Anthropic, Gemini, local OpenAI-compatible, Bedrock). Swap the model without rewriting the app.
    2. Tool-schema generation. Turn a typed Python function into the JSON Schema the model needs (52), from signatures and docstrings, instead of hand-writing it.
    3. The loop. The model → tool → observation → model cycle, the stop condition, and the step budget (52) — built, tested and reused.
    4. State and memory. Conversation history, scratchpads, summarisation of old turns, long-term memory stores.
    5. Multi-agent orchestration. Patterns for several agents — orchestrator–workers, pipelines, critics (52) — with the message plumbing between them.
    6. Retrieval integrations. Connectors to vector stores, rerankers and document loaders for RAG (51 — RAG).
    7. Streaming. Token and event streaming to the client, including partial tool calls.
    8. Tracing / observability. Spans for each model and tool call, token counts, latencies — locally or to a hosted backend (§18.1).
    9. Durable execution and human-in-the-loop. Checkpoint a long run, pause for approval, resume after a crash (52).
    10. Deployment. A server, a REST/streaming API, session storage, sometimes a UI.

    1.2 What a framework costs¶

    Nothing on that list is free. The costs are real and recurring:

    • Abstraction you must debug through. When the agent misbehaves, the bug is in your prompt, the model, or the framework's hidden glue — and the framework's call stack is between you and the HTTP request. The hand-written baseline of §2.1 has no such layer.
    • Churn and breaking changes. These libraries move monthly. An API you learned in the spring is deprecated by the autumn (you will see one such rename in §4). Pin versions (§18.4).
    • Lock-in. Your tools, prompts and state live inside the framework's types. Leaving means a rewrite — unless you wrapped it (§19).
    • Hidden prompts. Many frameworks inject their own system prompt, output-format instructions and few-shot examples. You did not write them, they count against your context and bill, and they change between versions. You will measure one at 3,544 characters in §9.
    • Dependency weight. A one-function feature can pull in hundreds of transitive packages, lengthening installs, container images and your security-review surface.
    • Performance. Extra Python per step, extra tokens per request. The Python is usually negligible; the tokens are not always. A local model must prefill every injected prompt token, and at the roughly 120 prompt tokens/s that 50 estimates for Qwen3-14B 4-bit on an M1 Pro, an 886-token framework prompt adds about 7 s to a call the server cannot serve from its prompt cache (§18.6).

    Warning

    The failure mode is adopting a multi-agent framework for a problem that is a single tool call in an existing service. You pay every cost above and use one item from the benefits list. §2 is the guard against that.

    1.3 A software analogy¶

    A framework is a web framework for agents. Writing the loop yourself is writing an HTTP server with the standard library: fine, educational, and sometimes exactly right for a tiny service. A framework is Django or Rails: it gives you routing, ORM, auth and admin, and in return you build it their way and upgrade when they say. You would not hand-roll HTTP for a large app; you also would not pull in Django to serve one static file.

    2. Do you need a framework?¶

    Start from the baseline and justify every departure from it.

    2.1 The no-framework baseline¶

    This is the whole agent for the running example of this chapter — answer a question about an order using two tools, get_order(order_id) and get_shipping_status(tracking_id) — in plain Python with the openai client. It is the yardstick every framework is measured against. (enable_thinking=False and the content or "" guard are explained in §14; keep them in mind.)

    import json
from openai import OpenAI

BASE = "http://127.0.0.1:8080/v1"          # the handbook's mlx_lm.server
MODEL = "mlx-community/Qwen3-14B-4bit"
client = OpenAI(base_url=BASE, api_key="local")


def get_order(order_id):
    return {"order_id": order_id, "status": "shipped", "amount": 129.99,
            "tracking_id": "TRK42", "_stub": "order_lookup_ok"}


def get_shipping_status(tracking_id):
    return {"tracking_id": tracking_id, "carrier": "UPS",
            "status": "in_transit", "eta": "2026-11-02",
            "_stub": "shipping_lookup_ok"}


TOOLS = [
    {"type": "function", "function": {
        "name": "get_order", "description": "Look up an order by id.",
        "parameters": {"type": "object",
                       "properties": {"order_id": {"type": "string"}},
                       "required": ["order_id"]}}},
    {"type": "function", "function": {
        "name": "get_shipping_status",
        "description": "Look up the shipping status for a tracking id.",
        "parameters": {"type": "object",
                       "properties": {"tracking_id": {"type": "string"}},
                       "required": ["tracking_id"]}}},
]
FUNCS = {"get_order": get_order, "get_shipping_status": get_shipping_status}


def run(task, max_steps=6):
    messages = [{"role": "user", "content": task}]
    for _ in range(max_steps):
        r = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS, temperature=0,
            extra_body={"chat_template_kwargs": {"enable_thinking": False}})
        msg = r.choices[0].message
        if not msg.tool_calls:
            return msg.content or ""
        messages.append(msg.model_dump(exclude_none=True))
        for tc in msg.tool_calls:
            args = json.loads(tc.function.arguments)
            obs = FUNCS[tc.function.name](**args)
            messages.append({"role": "tool", "tool_call_id": tc.id,
                             "content": json.dumps(obs)})
    return None


print(run("Where is my order A1001?"))

    Order A1001 shipped via UPS (tracking TRK42) and is in transit, ETA 2026-11-02. Amount charged: $129.99.

    That is 43 lines of code (54 with blank lines). It generates no schema for you — you wrote TOOLS by hand — and it owns its own loop. Every framework below shrinks that wiring; the question is whether the shrink is worth the costs of §1.2.

    Note

    The output above came from a local stub standing in for mlx_lm.server (10 — Export and serving): it returns a get_order tool call, then a get_shipping_status call once the first tool's result is in the request, then a canned final sentence. The stub only moves on when it sees the tools' return values, so the code really ran both tools. Every Python framework run in this chapter was pointed at the same stub (DSPy at a variant that speaks its text format, §10) and printed the same answer, because the sentence is the stub's. A real Qwen3-14B should produce the same shape for this task (two tool calls, one answer), in its own words. The stub also imitates Qwen3's default thinking behaviour (§14).

    2.2 The decision procedure¶

    Work top to bottom; stop at the first "yes".

    1. Is it a single call or a fixed workflow? Classify a ticket, extract invoice fields, a two-step extract-then-draft chain (52). → No framework. The openai client plus a for loop is less code than learning one, and you can read it.
    2. Is it one tool-calling feature inside an existing service? → No framework, or the thinnest possible one. Add the tool round trip (50) to the code you have. A framework's server, state model and deployment story are things you already own.
    3. Does the path genuinely depend on intermediate results you cannot enumerate, over many steps? → A lightweight agent library (§7) earns the loop, retries and schema generation.
    4. Do you need durable, resumable, human-gated workflows (hours-long runs, approvals, crash recovery)? → A graph/state-machine or durable-execution framework (§4, §11).
    5. Is retrieval the core of the product (RAG over documents)? → A data/RAG framework (§6).
    6. Do genuinely separate roles with different tools help, proven by an eval? → A multi-agent framework (§5) — but re-read 52 first; most "multi-agent" problems are one agent with good tools.
    7. Are non-engineers building the automations? → A low-code builder (§13).

    The honest default for an engineer with a model endpoint and a product is 1 or 2. Reach higher only when a concrete need on the list pulls you there.

    3. The categories¶

    Every framework in this chapter sits in one of these buckets. The bucket predicts its shape far better than its marketing does.

    Category What it is for Frameworks (this chapter)
    Graph / state-machine orchestration Explicit control flow, durable state, resumable graphs LangGraph, LangChain
    Role-based multi-agent Crews of role-playing agents with tasks CrewAI
    Data / RAG-centric Retrieval and document pipelines first, agents second LlamaIndex, Haystack
    Typed / lightweight agent libraries A thin, typed loop over tools Pydantic AI, Agno
    Vendor agent SDKs A model or cloud vendor's own agent layer OpenAI Agents SDK, Microsoft Agent Framework, Google ADK, AWS Strands, Claude Agent SDK
    Code-agent libraries The model writes code that calls tools smolagents
    Prompt-optimization / programming Compile and optimise prompts from typed signatures DSPy
    Stateful / durable-execution platforms Persistent agent state; crash-safe long runs Letta; Temporal, DBOS, Inngest, Restate
    TypeScript frameworks Agents inside a JS/TS product Mastra, Vercel AI SDK
    Low-code / visual builders Drag-and-drop for non-engineers n8n, Dify, Flowise, Langflow

    Every per-framework section below uses the same ten-part structure: what it is and who maintains it; the mental model in two or three sentences; a minimal example (run against the stub for the Python libraries that install cleanly); strengths; weaknesses ("minuses"); use it when; avoid it when; local OpenAI-compatible models (yes/no/how — see §14); MCP support (58); licence.

    4. Graph / state-machine orchestration: LangGraph & LangChain¶

    4.1 LangGraph¶

    What and who. LangGraph is a low-level orchestration runtime for stateful, multi-step agents, maintained by LangChain Inc. It reached v1.0 in October 2025 (the version used here is 1.2.18) with a stability commitment: no breaking changes until 2.0.

    Mental model. You describe the agent as a graph: nodes are functions (call the model, run a tool), edges are the control flow, and a shared typed state object flows through them. A checkpointer persists that state after every node, so a run can be interrupted for human approval and resumed later — even after a crash. For the common case, LangChain's create_agent (§4.2) builds a ready-made ReAct-style graph for you.

    Minimal example (run against the stub; langchain 1.4.7 + langgraph 1.2.18):

    import os
os.environ["OPENAI_API_KEY"] = "local"
from langchain_openai import ChatOpenAI
from langchain.agents import create_agent

BASE = "http://127.0.0.1:8080/v1"
MODEL = "mlx-community/Qwen3-14B-4bit"


def get_order(order_id: str) -> dict:
    """Look up an order by id; returns its status, amount and tracking_id."""
    return {"order_id": order_id, "status": "shipped", "amount": 129.99,
            "tracking_id": "TRK42", "_stub": "order_lookup_ok"}


def get_shipping_status(tracking_id: str) -> dict:
    """Look up the shipping status for a tracking id."""
    return {"tracking_id": tracking_id, "carrier": "UPS",
            "status": "in_transit", "eta": "2026-11-02",
            "_stub": "shipping_lookup_ok"}


llm = ChatOpenAI(
    model=MODEL, base_url=BASE, api_key="local", temperature=0,
    extra_body={"chat_template_kwargs": {"enable_thinking": False}})
agent = create_agent(llm, tools=[get_order, get_shipping_status])

result = agent.invoke(
    {"messages": [{"role": "user", "content": "Where is my order A1001?"}]})
print(result["messages"][-1].content)

    Order A1001 shipped via UPS (tracking TRK42) and is in transit, ETA 2026-11-02. Amount charged: $129.99.

    Strengths. Mature durable state and checkpointing; first-class human-in-the-loop (interrupt) and time-travel/replay; explicit control flow you can see and test; deep LangSmith tracing; a large ecosystem. Minuses. The graph/state mental model is a real learning curve; the wider LangChain ecosystem has renamed and retired APIs often (AgentExecutor → legacy, create_react_agent → create_agent); easy to over-engineer a problem that was a single call. Use it when. Long-running, resumable, human-gated workflows; branching control flow; you want checkpointing without building it. Avoid it when. A single tool-calling feature — the graph is overhead you will debug through. Local models. Yes — ChatOpenAI(base_url=…, extra_body=…) points at mlx_lm.server and passes enable_thinking (§14). MCP. Yes, via the langchain-mcp-adapters package (load MCP servers' tools into the graph). Licence. MIT.

    4.2 LangChain¶

    What and who. LangChain is the high-level library (chains, prompts, model wrappers, hundreds of integrations) from the same company; it reached v1.0 in October 2025 alongside LangGraph. As of 1.x, LangChain's agents run on the LangGraph runtime — create_agent is a thin, opinionated layer over a LangGraph graph. The pre-1.0 AgentExecutor style is legacy; the 0.3 line is in maintenance until December 2026.

    Mental model. LangChain is the "batteries-included" surface — model abstraction, prompt templates, retrievers, output parsers, and the init_chat_model/create_agent conveniences — while LangGraph is the engine underneath. Use LangChain's pieces to assemble; drop to LangGraph when you need custom control flow.

    Minimal example. Identical to §4.1: create_agent is imported from langchain.agents and is the same call shown above. (That the LangGraph example's import moved from langgraph.prebuilt.create_react_agent to langchain.agents.create_agent between versions is a concrete taste of the churn in §1.2.)

    Strengths. One of the broadest integration catalogues (hundreds of provider, vector-store and tool packages); a quick way to wire a model, a retriever and tools together; shares LangGraph's runtime and LangSmith tracing. Minuses. Breadth means surface area and version drift; the 1.x stability promise covers langchain and langchain-core, while langchain-community is still on 0.x (0.4.2 in October 2026) and outside it; the many layers can obscure the one HTTP request you care about. Use it when. You want conveniences and integrations and are comfortable on the LangChain/LangGraph stack. Avoid it when. You want a minimal dependency footprint, or you dislike debugging through layers. Local models / MCP / Licence. Same as LangGraph: OpenAI-compatible via ChatOpenAI; MCP via langchain-mcp-adapters; MIT.

    5. Role-based multi-agent: CrewAI¶

    What and who. CrewAI is a standalone multi-agent framework (not built on LangChain) from CrewAI Inc., version 1.15.32 here.

    Mental model. You define agents with a role, goal and backstory, give each some tools, and compose tasks into a crew that runs them sequentially or hierarchically. It leans on role-play: the personas shape behaviour. Under the hood, CrewAI 1.x calls providers through its own native integrations (the openai/ prefix selects its OpenAI provider, which honours base_url), with LiteLLM as an optional extra for other providers, so any OpenAI-compatible endpoint works.

    Minimal example (run against the stub; crewai 1.15.32). One agent, two tools — the same task, to keep the comparison honest:

    from crewai import Agent, Task, Crew, LLM
from crewai.tools import tool

BASE = "http://127.0.0.1:8080/v1"
MODEL = "mlx-community/Qwen3-14B-4bit"


@tool("get_order")
def get_order(order_id: str) -> dict:
    """Look up an order by id; returns status, amount and tracking_id."""
    return {"order_id": order_id, "status": "shipped", "amount": 129.99,
            "tracking_id": "TRK42", "_stub": "order_lookup_ok"}


@tool("get_shipping_status")
def get_shipping_status(tracking_id: str) -> dict:
    """Look up the shipping status for a tracking id."""
    return {"tracking_id": tracking_id, "carrier": "UPS",
            "status": "in_transit", "eta": "2026-11-02",
            "_stub": "shipping_lookup_ok"}


llm = LLM(model="openai/" + MODEL, base_url=BASE, api_key="local",
          temperature=0,
          extra_body={"chat_template_kwargs": {"enable_thinking": False}})
agent = Agent(role="Support agent",
              goal="Answer order questions using the tools.",
              backstory="You help customers track their orders.",
              tools=[get_order, get_shipping_status], llm=llm, verbose=False)
task = Task(description="Where is my order A1001?",
            expected_output="A one-sentence status with carrier and ETA.",
            agent=agent)
crew = Crew(agents=[agent], tasks=[task], verbose=False)
print(crew.kickoff())

    Order A1001 shipped via UPS (tracking TRK42) and is in transit, ETA 2026-11-02. Amount charged: $129.99.

    (CrewAI logs an "approximate input token count" warning to stderr for model names it does not know; stdout is the single line above.)

    Strengths. The role/task/crew model is intuitive and reads like an org chart; fast to stand up a plausible multi-agent demo; a large templates-and-tools ecosystem; a separate CrewAI Flows API for deterministic control when you need it. Minuses. Role prompts do not enforce structure: outside Flows, the model decides the control flow, so crews can loop and spend tokens (52); the persona abstraction hides the prompts (the run above sent a persona system message and task framing you did not write, §18.6). Use it when. Genuinely separable roles with distinct tools, and a demo-to-prototype pace matters. Avoid it when. The task is one agent's job (as above) — you pay the multi-agent tax for nothing; or you need tight, auditable control flow. Local models. Yes — LLM(model="openai/…", base_url=…, extra_body=…) through CrewAI's native OpenAI provider. MCP. Yes — natively through the agent's mcps field, or MCPServerAdapter from crewai-tools. Licence. MIT.

    6. Data / RAG-centric frameworks: LlamaIndex & Haystack¶

    6.1 LlamaIndex¶

    What and who. LlamaIndex (LlamaIndex Inc.) is a data framework for LLM applications — ingestion, indexing, retrieval — that grew an agent layer. Core version 0.14.25 here.

    Mental model. Everything is organised around getting your data to the model: loaders → nodes → indexes → retrievers → query engines, with Workflows (an event-driven, step-based engine) as the orchestration layer and FunctionAgent/AgentWorkflow as agents built on it. If the product is "answer from my documents", LlamaIndex is shaped for it.

    Minimal example (run against the stub; llama-index 0.14.25, llama-index-llms-openai-like 0.8.0). FunctionAgent.run is async:

    import asyncio
from llama_index.core.agent.workflow import FunctionAgent
from llama_index.llms.openai_like import OpenAILike

BASE = "http://127.0.0.1:8080/v1"
MODEL = "mlx-community/Qwen3-14B-4bit"


def get_order(order_id: str) -> dict:
    """Look up an order by id; returns status, amount and tracking_id."""
    return {"order_id": order_id, "status": "shipped", "amount": 129.99,
            "tracking_id": "TRK42", "_stub": "order_lookup_ok"}


def get_shipping_status(tracking_id: str) -> dict:
    """Look up the shipping status for a tracking id."""
    return {"tracking_id": tracking_id, "carrier": "UPS",
            "status": "in_transit", "eta": "2026-11-02",
            "_stub": "shipping_lookup_ok"}


llm = OpenAILike(
    model=MODEL, api_base=BASE, api_key="local",
    is_chat_model=True, is_function_calling_model=True, temperature=0,
    additional_kwargs={"extra_body": {
        "chat_template_kwargs": {"enable_thinking": False}}})
agent = FunctionAgent(tools=[get_order, get_shipping_status], llm=llm)


async def main():
    resp = await agent.run("Where is my order A1001?")
    print(str(resp))


asyncio.run(main())

            "status": "in_transit", "eta": "2026-11-02",

    DSPy does not send native tool calls; its ChatAdapter asks the model to emit [[ ## field ## ]] blocks (next_thought, next_tool_name, next_tool_args, then a separate reasoning/answer extract step).     11. Stateful and durable-execution platforms¶

    Two related needs: persistent agent state (the agent remembers across sessions) and durable execution (a long run survives crashes and restarts).

    11.1 Letta (formerly MemGPT)¶

    What and who. Letta (the company and framework that grew out of UC Berkeley's MemGPT research, renamed September 2024) is built around stateful agents with self-editing memory. Its current open-source code is Letta Code (letta-ai/letta-code, npm @letta-ai/letta-code, Apache-2.0): an agent harness with a terminal UI, an App Server you can self-host, channels and SDKs. The original Python API server ("Letta V1") is retired to an archive branch of letta-ai/letta. Letta Cloud, which stores agent state for you, is the default backend; a local backend is an option.

    Mental model. The agent owns a structured, persistent memory (memory blocks plus searchable history), stored by the Letta backend and edited by the agent itself; you talk to that backend (Letta Cloud or your own App Server), which keeps the state, so agents live beyond a single process.

    Minimal example. Not run here: Letta is server-centric (you run an App Server or use Letta Cloud and talk to it over its API/SDK), which is outside this chapter's single-process stub test. See https://docs.letta.com/ for the current client snippet.

    Strengths. Persistent, self-editing memory is the core of the design, not an add-on; agents retain state across sessions and restarts; self-hostable and open. Minuses. The server/stateful model is heavier to operate than a library; the project's focus and APIs have moved quickly (MemGPT → Letta server → Letta Code); you adopt its memory abstraction. Use it when. Long-lived assistants that must remember users and facts across sessions. Avoid it when. Stateless request/response, or you do not want to run a stateful server. Local models. Yes, with limits — a local backend can use the built-in Ollama or LM Studio providers, and an OpenAI-compatible custom provider can be added with /connect (for a Cloud-hosted agent the endpoint must be reachable from the internet, not localhost). MCP. Yes on the Letta platform (register MCP servers; Streamable HTTP recommended), though for Letta Code its docs recommend skills instead of MCP. Licence. Apache-2.0 (Letta Code; Letta Cloud is a hosted service).

    11.2 Durable-execution platforms (Temporal, DBOS, Inngest, Restate)¶

    These are not agent frameworks; they are workflow engines you wrap an agent in so a long, multi-step run is crash-safe and resumable. The pattern: each model call and tool call is a durably-recorded step, so if the process dies mid-run it replays deterministically from the last completed step — the durable-execution version of 52's pause-and-resume.

    • Temporal — the mature, self-hostable/managed workflow engine; its SDKs now have agent-oriented helpers. Heavy but battle-tested.
    • DBOS — durable execution as a library backed by Postgres; lighter to adopt.
    • Inngest — event-driven durable functions, popular in the TypeScript world.
    • Restate — a newer durable-execution runtime.

    Use them when a run lasts minutes to hours, must survive restarts, or needs exactly-once side effects. LangGraph's checkpointer covers much of this inside one process; a durable-execution platform covers it across process and machine failures. Verify each project's current licence before adopting (several mix open-source cores with commercial cloud tiers).

    14. Local models: the thinking trap¶

    The handbook serves Qwen3-14B through mlx_lm.server (10 — Export and serving), an OpenAI-compatible endpoint. Two things about a local, thinking-capable model cut across every framework, so "local-model friendliness" is a real selection criterion — not an afterthought.

    14.1 Qwen3 thinks by default¶

    Qwen3 emits a reasoning block before its answer. Through an OpenAI-compatible server, a request without thinking control can return message.content = null, or content that starts with <think>…, and that can confuse naive tool-call parsing and answer extraction. The handbook convention is to pass chat_template_kwargs={"enable_thinking": False} in the request body (with the openai client: extra_body={"chat_template_kwargs": {"enable_thinking": False}}) when you want direct answers and tool calls — and to guard content or "" everywhere, because content can be None.

    This demo (run against the stub, which imitates a server that leaves Qwen3's think block in content) shows the difference on the final answer:

    import json
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8080/v1", api_key="local")
MODEL = "mlx-community/Qwen3-14B-4bit"


def final_answer(extra):
    msgs = [
        {"role": "user", "content": "Where is order A1001?"},
        {"role": "assistant", "content": None, "tool_calls": [
            {"id": "t1", "type": "function", "function": {
                "name": "get_shipping_status",
                "arguments": '{"tracking_id": "TRK42"}'}}]},
        {"role": "tool", "tool_call_id": "t1",
         "content": json.dumps({"carrier": "UPS", "status": "in_transit",
                                "_stub": "shipping_lookup_ok"})},
    ]
    r = client.chat.completions.create(model=MODEL, messages=msgs,
                                       temperature=0, **extra)
    return (r.choices[0].message.content or "")


on = final_answer({})
off = final_answer(
    {"extra_body": {"chat_template_kwargs": {"enable_thinking": False}}})
print("default  :", repr(on[:22]))
print("no-think :", repr(off[:22]))

    default  : '<think>\nThe task needs'
no-think : 'Order A1001 shipped vi'

    With thinking on, this answer begins with a <think> block you must strip; with enable_thinking=False, it is the clean answer (the sentence itself is the stub's canned text). Servers that leave the think block in content behave like this stub. mlx_lm.server 0.32.2 instead moves the reasoning into a separate reasoning field (50 — Prompting and APIs), so there content stays clean, or is None on a turn that only called a tool or ran out of max_tokens while thinking. The thinking tokens are still generated either way, so you wait for them and they can use up a small max_tokens. Turning thinking off for tool loops and guarding None is the fix that works on every server (see 10 §4 for --chat-template-args, which sets it server-wide).

    18. Cross-cutting concerns¶

    These apply whatever framework you pick (or none).

    18.1 Observability¶

    You cannot operate what you cannot see. Three neutral facts: the industry is converging on the OpenTelemetry GenAI semantic conventions (standard span/attribute names for model and tool calls), so prefer frameworks that emit them; Langfuse, LangSmith (LangChain's) and Arize Phoenix are widely used tracing/eval backends, and most frameworks have an integration for at least one. Pydantic AI leans on Logfire, DSPy on MLflow, OpenAI Agents and Strands emit traces natively. Whatever you choose, capture per-step spans with token counts and latency, and wire them into production observability (55 — Production §observability).

    18.2 Evaluation¶

    A framework does not make your agent correct — an eval does. Treat evals as tests whose assertions are thresholds (54 — Evaluation): a golden set of tasks, reference or LLM-judge scoring, run in CI. Several frameworks ship eval helpers (ADK, Mastra, DSPy's optimisers, LangSmith datasets), but the discipline matters more than the tool. Evaluate the whole system — model + prompt + tools + framework glue — not the model in isolation, exactly as 11 §9 evaluates the agent loop rather than the endpoint.

    18.3 Testing agents built on frameworks¶

    The techniques are framework-independent:

    • Mock the model. Replace the model with a scripted fake that returns fixed tool calls and answers (52 uses exactly this), so the loop, dispatch and parsing are tested deterministically with no network.
    • Record/replay. Capture real model responses once, then replay them in tests — fast, deterministic, and it catches regressions in your glue.
    • A stub endpoint. The approach this whole chapter used: a tiny OpenAI-compatible server that returns canned tool calls and answers (50 on the request shape). It let eleven frameworks and the baseline run the same task offline (DSPy against a variant that speaks its text format), and it is how you'd test a framework-based agent in CI without a GPU. Make the stub advance only when it sees your tools' real return values, as this one did, so a passing run proves the tools were called.
    • Test tools in isolation. Your get_order is ordinary code — unit-test it without the model.

    18.4 Managing upgrades¶

    Given the churn (§1.2): pin exact versions (you saw create_react_agent move to create_agent between LangGraph/LangChain versions, Pydantic AI already on 2.x, DSPy on 3.x, ADK and Haystack with new major versions in 2026). Read release notes before bumping. And wrap the framework behind your own interface — a thin Agent class of yours that the rest of the app calls — so a breaking change or a framework swap touches one module, not the whole codebase (§19).

    18.5 Security¶

    Frameworks concentrate the risks of 56 — Safety and security, so they deserve extra care:

    • Hidden prompts are attack surface. The framework's injected system prompt is text you did not audit; indirect prompt injection from tool outputs still applies (56).
    • Tool permissions. A framework makes it easy to hand the model many tools; the fewer and more typed, the smaller the blast radius (11 §4, 52). Keep the policy layer in your code, not a prompt.
    • Code-execution agents need sandboxes. A CodeAgent (§9) runs model-written code; never run it unsandboxed. Use the framework's sandbox backends (E2B/Modal/Docker/Pyodide) and treat the output as untrusted.
    • Dependency risk. Hundreds of transitive packages are a supply-chain surface; review them.

    18.6 Cost and token overhead¶

    Framework system prompts cost real tokens on every call. Measured here (the stub logged each request): LangGraph, LlamaIndex, Haystack, Pydantic AI, Agno, OpenAI Agents and Strands sent no system prompt of their own; CrewAI sent a 124-character persona system message (plus task framing in the user turn) and ADK a 50-character one; DSPy's adapter sent a 2,265-character format prompt on each ReAct step, because the tool descriptions and field format live in its prompt rather than in a tools field. smolagents' ToolCallingAgent sent a 3,544-character system prompt, the largest of the runs, and its first request was 4,872 bytes versus the baseline's 602. A CodeAgent with the same two tools sends 8,814 characters.

    On paper

    smolagents' ToolCallingAgent sends a 3544-character system prompt. At about 4 characters per token, over the 3 model calls this task takes:

    \[ \begin{aligned} \text{tokens} &\approx 3544 / 4 = 886\\ \text{per task} &\approx 3 \times 886 = 2658 \end{aligned} \]

    Each call carries about 886 tokens of scaffolding, about 5% of a 16K window, and the task makes the model read about 2,700 of them in total. On a local model that is prefill time: at roughly 120 prompt tokens/s (Qwen3-14B 4-bit on an M1 Pro, 50), 886 tokens take about 7 s on any call that the server's prompt cache cannot serve.

    On paper

    The stub logged smolagents' first request at 4872 bytes and the baseline's at 602:

    \[ 4872 / 602 \approx 8.1 \]

    Eight times the bytes on the wire. Most of the 4,270 extra bytes are the 3,544-character system prompt; the rest is its final_answer tool and longer tool descriptions. Most frameworks add little; smolagents trades tokens for its reasoning scaffold. Measure yours — do not assume it is zero.

    If you pay per token, that overhead has a price. Hosted-model prices move, so treat the number as an assumption, not a fact:

    On paper

    Assume $0.50 per million input tokens. With 2658 scaffold tokens per task and 100,000 tasks a day:

    \[ \begin{aligned} \text{per task} &\approx 2658/10^6 \times 0.50 \approx 0.0013\\ \text{per day} &\approx 10^5 \times 0.001329 \approx 133 \end{aligned} \]

    About $133 a day is the framework's system-prompt tax alone (before any prompt-cache discount), before your own prompt and the outputs. For a local model the cost is latency and context instead of dollars, but it is just as real.

    19. Migration paths¶

    19.1 From no framework to a framework¶

    You start with the baseline (§2.1) and outgrow it (you need durable state, or multi-agent, or RAG). The migration is mechanical because the pieces map:

    • Your tool functions become the framework's tools (usually just a decorator or passing the function).
    • Your hand-written TOOLS schema is deleted — the framework generates it from signatures and docstrings. (So keep good type hints and docstrings even in the baseline.)
    • Your run() loop becomes the framework's agent/runner.
    • Your extra_body for enable_thinking moves to the framework's model-settings call (§14.2).

    Migrate behind your eval (§18.2): the answers should stay correct (against the stub every framework above printed the identical output; against a real model the wording can change, which is why you check with the eval rather than a string compare), so the eval catches any regression the migration introduces.

    19.2 From a framework back to no framework (or to another)¶

    This is the one teams underestimate. If the framework's abstractions fight you, or it churns too hard, you may want out. It is painful only if you coupled to it everywhere. The defence is an adapter layer: define your own small interface, make it the only module that imports the framework, and keep everything else depending on your type. Here the adapter wraps Pydantic AI (§7.1); the shape is the same whatever you wrap:

    import os
os.environ["PYDANTIC_AI_NO_BANNER"] = "1"
from typing import Protocol
from pydantic_ai import Agent
from pydantic_ai.models.openai import OpenAIChatModel, OpenAIChatModelSettings
from pydantic_ai.providers.openai import OpenAIProvider

BASE = "http://127.0.0.1:8080/v1"
MODEL = "mlx-community/Qwen3-14B-4bit"


class OrderAgent(Protocol):
    def answer(self, question: str) -> str: ...


def get_order(order_id: str) -> dict:
    """Look up an order by id; returns status, amount and tracking_id."""
    return {"order_id": order_id, "status": "shipped", "amount": 129.99,
            "tracking_id": "TRK42", "_stub": "order_lookup_ok"}


def get_shipping_status(tracking_id: str) -> dict:
    """Look up the shipping status for a tracking id."""
    return {"tracking_id": tracking_id, "carrier": "UPS",
            "status": "in_transit", "eta": "2026-11-02",
            "_stub": "shipping_lookup_ok"}


class PydanticAIOrderAgent:
    """The only class (in the only module) that touches the framework."""
    def __init__(self, tools):
        model = OpenAIChatModel(
            MODEL, provider=OpenAIProvider(base_url=BASE, api_key="local"))
        settings = OpenAIChatModelSettings(
            extra_body={"chat_template_kwargs": {"enable_thinking": False}})
        self._agent = Agent(model, tools=tools, model_settings=settings)

    def answer(self, question: str) -> str:
        return self._agent.run_sync(question).output


agent: OrderAgent = PydanticAIOrderAgent([get_order, get_shipping_status])
print(agent.answer("Where is my order A1001?"))

    Order A1001 shipped via UPS (tracking TRK42) and is in transit, ETA 2026-11-02. Amount charged: $129.99.

    The rest of your app depends on OrderAgent and your plain tool functions, not on Pydantic AI, LangGraph or CrewAI. Swapping frameworks — or dropping back to the baseline loop of §2.1 — then means writing one new class with the same answer method, with your eval proving the behaviour held. This also neutralises the upgrade churn of §18.4: a breaking change lands in one file.

    Tip

    Write the adapter on day one, even if you are sure of your framework choice. It costs about a dozen lines — the Protocol and the wrapper class above — and buys you an exit. The frameworks took 19 to 34 lines for this task; the wrapper adds only that dozen on top of whichever one you pick.

    20. Key takeaways¶

    • A framework is leverage you rent: it removes boilerplate (schema generation, the loop, state, streaming, tracing) and in exchange you debug through its abstractions and ride its upgrade treadmill. Justify every departure from the ~43-line baseline.
    • Most "agent" problems are a single call or a fixed workflow (52). Use the least autonomy — and the least framework — that solves the task.
    • Pick by category, then by fit: graph/state-machine (LangGraph), role multi-agent (CrewAI), data/RAG (LlamaIndex, Haystack), typed/light (Pydantic AI, Agno), vendor SDKs (OpenAI Agents, MS Agent Framework, Google ADK, AWS Strands, Claude Agent SDK), code-agent (smolagents), prompt-opt (DSPy), stateful (Letta), TypeScript (Mastra, Vercel AI SDK), low-code (Langflow/n8n/Dify; Flowise is archived).
    • Status changed in 2025–2026: AutoGen and Semantic Kernel → Microsoft Agent Framework (AutoGen archived, Semantic Kernel on critical and security fixes); LangChain 1.x runs on LangGraph; the Claude Code SDK → Claude Agent SDK; Flowise archived; Letta's server gave way to Letta Code.
    • Local, thinking models are a real criterion. Qwen3 thinks by default; pass chat_template_kwargs={"enable_thinking": False} and guard content or "". Every Python framework here can thread that through extra_body; one that can't is a red flag (§14).
    • Measure the overhead. System-prompt tokens are real (3,544 chars / ~886 tokens per call for smolagents here); so is lines-of-code; so is churn. Numbers beat vibes.
    • Wrap the framework behind your own interface and pin versions, so a breaking change or a framework swap touches one module (§19).
    • Licences matter for shipping: most libraries are MIT or Apache-2.0; n8n and Dify add commercial restrictions (source-available, and modified Apache-2.0); the Claude Agent SDK is under Anthropic's commercial terms; Flowise is archived.

    21. Exercises¶

    Exercise 21.1

    You are adding "summarise this ticket and tag its priority" to an existing support service. Which framework do you reach for, and why?

    Answer

    None. That is a single model call (or a two-step extract-then-classify workflow), not an agent (52). The openai client plus the structured-output pattern (50) is fewer lines than learning a framework, has no hidden prompt, and you already own the service's deployment and state. Reach for a framework only when the decision procedure of §2.2 pulls you past step 2.

    Exercise 21.2

    The same two-tool order task is 43 lines in the no-framework baseline and 19 in Agno. Compute the ratio and say what the saved lines cost you.

    Answer

    \(43 / 19 \approx 2.3\). The baseline is about 2.3x larger, mostly because it hand-writes the TOOLS JSON schema and the loop, which Agno generates from signatures and owns internally. The saved lines cost you an abstraction layer to debug through, a hidden system prompt, a dependency tree, and an upgrade treadmill (§1.2). Worth it when you need the batteries; not worth it for a single call.

    Exercise 21.3

    Your agent, on a local Qwen3-14B, sometimes returns an empty or <think>…-prefixed answer through the framework. What are the two fixes, and how do you apply them in (a) the raw openai client and (b) LangGraph?

    Answer

    (1) Disable thinking by passing chat_template_kwargs={"enable_thinking": False}; (2) guard content or "" because content can be None. In the raw client: create(..., extra_body={"chat_template_kwargs": {"enable_thinking": False}}). In LangGraph: ChatOpenAI(..., extra_body={"chat_template_kwargs": {"enable_thinking": False}}). See §14; every Python framework here exposes extra_body by some name.

    Exercise 21.4

    smolagents' ToolCallingAgent system prompt measured 3,544 characters. Estimate the token overhead per task if the task takes 3 model calls, at ~4 characters per token.

    Answer

    \(3544 / 4 = 886\) tokens per call, and \(3 \times 886 = 2658\) tokens per task — about 2,700 tokens of scaffolding the model must read before it gets to the order data. Each call's 886 tokens are about 5% of a 16K window, and at roughly 120 prompt tokens/s of local prefill they add about 7 s to every call the prompt cache cannot serve (§18.6). A CodeAgent sends 8,814 characters, about 2,200 tokens per call; it can still be worth it when composing several tool calls in one code step saves round trips — measure both.

    Exercise 21.5

    A teammate proposes a three-agent CrewAI "crew" (researcher, writer, reviewer) for a task a single agent handles today. Each agent step succeeds with probability 0.98. What happens to reliability and cost, and what do you ask for before agreeing?

    Answer

    Reliability compounds down with more steps (52): a single call is \(0.98\), while a naive 5-step three-agent flow is about \(0.98^5 \approx 0.904\) — and each agent re-sends its own context, so cost and latency multiply. Ask for an eval (§18.2) showing the crew beats the single agent on the real task. If it does not, the extra agents are cost and coordination risk for nothing (52).

    Exercise 21.6

    You built on AutoGen a year ago. What is the current status, and what should you do?

    Answer

    AutoGen is archived: its README says Microsoft no longer provides bug fixes, security fixes, new features or support, and names the Microsoft Agent Framework (GA April 2026; agent-framework on PyPI) as its successor, with an AutoGen migration guide (§8.2). Without security fixes, staying put is a growing risk, so plan the migration as scheduled work: put an adapter around the AutoGen code first (§19.2), port behind your eval, then switch. (Had you built on Semantic Kernel instead, you would have more time: it still gets critical and security fixes for at least a year after the Agent Framework's GA.) This is the churn risk of §1.2 made concrete.

    Exercise 21.7

    Why is "wrap the framework behind your own interface" worth a dozen lines on day one?

    Answer

    Because it localises both risks of §1.2: a breaking upgrade or a decision to swap frameworks (or drop back to the baseline) touches one adapter module instead of the whole codebase (§19.2). The frameworks here took 19 to 34 lines for the task (the baseline 43); the wrapper adds about a dozen lines on top of any of them, and your eval proves behaviour held across the swap.

    Exercise 21.8

    You need RAG over company docs and a long-running, human-approved workflow around it. One framework, or two layers?

    Answer

    Two concerns, so consider two layers: a data/RAG framework for retrieval (§6 — LlamaIndex or Haystack) and a graph/state-machine for the durable, human-gated workflow (§4.1 — LangGraph's checkpointer + interrupt). LangGraph can call a LlamaIndex/Haystack retriever as a tool. If retrieval is simple, one framework with a retrieval integration may suffice; if the workflow is simple, add retrieval to a lighter agent. Let the dominant concern pick the primary framework, and keep both behind your adapter (§19.2).

    Exercise 21.9

    You want to ship a visual agent builder inside your commercial SaaS so customers can build flows. Which low-code tool's licence is safest, and which should you avoid?

    Answer

    Langflow is MIT, a permissive licence that allows embedding in a product. n8n (Sustainable Use License, source-available) and Dify (its "Open Source License": Apache-2.0 plus extra conditions) restrict reselling, multi-tenant use or embedding — read them before shipping, and get written permission or a commercial licence if needed. Flowise was archived on 13 August 2026 and gets no fixes — do not build new on it (§13).

    Exercise 21.10

    How did this chapter test eleven frameworks' agents (plus the baseline) without a GPU or a hosted model, and why does that generalise to testing your own framework-based agent?

    Answer

    With a stub OpenAI-compatible server that returns canned tool calls and a final answer, driven by sentinels — marker strings that only the tools' return values contain — so it advances only after each tool has really run (§2.1 note, §18.3); DSPy used a variant that speaks its text format. Each framework was pointed at it and printed the identical answer (the stub's canned sentence), offline and deterministically. The same technique tests your production agent: mock the model (or stub the endpoint), record/replay real responses, and unit-test the tools as ordinary code — so your CI exercises the loop and the glue without a model at all.
